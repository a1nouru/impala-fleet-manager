# Nilo Inventory — implementation plan (2026-11-03)

One shared parts inventory owned by **Nilo** (the garage), reachable from both the
Royal Express and Impala fleet managers ("Nilo Inventory" tab). Every physical unit
carries a system-generated QR label, so each part is traceable from invoice to vehicle.
Nilo bills each company monthly for what it consumed.

## Decisions (locked with user)
| Topic | Decision |
|---|---|
| Stock owner | Nilo. Companies only *consume*; each consumption is tagged with company + vehicle. |
| Shared stock | ONE pool. Both apps read the same Nilo balance live, so a part Impala uses is immediately gone from Royal's "available" (and vice versa). No per-company stock, no sync job. |
| QR | Generated by the system, one per unit, bound to an invoice line before printing. |
| Bulk (oil, silicone…) | One QR per container; usage records a measured quantity (L / tubes); container closes at 0. |
| Access | Inside both apps (existing logins). No separate Nilo app. |
| Printing | A4 sticker sheets, normal printer, browser print. |
| Invoice checks | Hard blocks + flags. Flagged invoices need approval by an allowlisted approver (Moise + nourumuneza@gmail.com). |
| Billing | Monthly statement per company, priced at unit cost from the invoice, AGRA-report design. Lots entered with margin (China/Roadking: cost + freight + 30%) bill at that margin-inclusive unit cost — no separate base/margin fields (decided 2026-11-09). |
| Mark paid | Approvers only; must attach the bank payment proof. |

## Flow
1. **Upload invoice** → OCR (Claude structured outputs, same stack as `app/api/slip-extract`) → checks.
2. **Checks**
   - BLOCK (cannot proceed): duplicate supplier NIF + invoice number; duplicate file SHA-256.
   - FLAG (needs approver): lines ≠ invoice total (±1 Kz); line IVA inconsistent; date in future or > 60 days old; qty/price = 0; any manual edit of OCR numbers.
   - Clean invoices auto-approve; flagged → `pending_approval` until an approver signs off (name + time recorded).
3. **Name lines** — user enters item name, unit vs bulk (+ container size/unit). Price is read-only from the invoice line.
4. **Generate & print labels** — N units per line → N QR codes (`NILO-000123`) on an A4 sticker sheet (QR + name + code + invoice no.).
5. **Receive** — scan each label onto the shelf → `in_stock`. Per-line progress "4/6 received".
6. **Consume** — in the maintenance form, "Scan part" → movement (company from app, vehicle, maintenance record, user). Bulk prompts for quantity. Also appends the legacy `"Name (Qty: N)"` string to `maintenance_records.parts` so existing reports/insights keep working.
7. **Trace** — scan/search a code → invoice, supplier, unit cost, received by/when, used on which vehicle/company/by whom.
8. **Statement** — month + company → frozen statement (number, lines, total) → PDF.

## Data — new dedicated Supabase project "nilo"
- `nilo_invoices` — supplier, supplier_nif, invoice_no, invoice_date, total, file_path, file_sha256, ocr_raw jsonb, checks jsonb, status (`blocked|pending_approval|approved`), approved_by, approved_at, uploaded_by, source_company. Unique (supplier_nif, invoice_no), unique (file_sha256).
- `nilo_invoice_lines` — invoice_id, ocr_description, quantity, unit_cost (IVA-incl), item_name, kind (`unit|bulk`), container_size, measure_unit, labels_generated.
- `nilo_units` — code (unique, `NILO-` + seq), line_id, invoice_id, unit_cost, status (`labelled|in_stock|consumed|void`), remaining (bulk).
- `nilo_movements` — append-only: unit_id, type (`receive|consume|adjust|void`), quantity, company (`royal|impala`), vehicle_plate, maintenance_record_id, user_email, created_at. No update/delete grants.
- `nilo_statements` — statement_no, company, period (month), lines jsonb snapshot, total, issued_by, issued_at, status (`issued|paid`), paid_by, paid_at, payment_proof_path, payment_proof_sha256. Immutable once issued; corrections via credit adjustments next month.
- Mark-as-paid: approvers only; REQUIRES attaching the bank payment statement/proof (PDF/image, stored in private bucket `nilo-payments`). Server rejects paid without a file.
- Private storage bucket `nilo-invoices`.
- RLS on, no anon/authenticated policies: only the server role touches it.

## Access model
- Each app gets `app/api/nilo/*` routes (Node runtime) — session-gated by the app's own Supabase auth, talking to Nilo with `NILO_SUPABASE_URL` + `NILO_SERVICE_ROLE_KEY`.
- `company` is set server-side from env `NILO_COMPANY=royal|impala` — never trusted from the client.
- Approver check server-side: session email ∈ `NILO_APPROVER_EMAILS` (comma list).
- Env on BOTH Railway services (RE = `resplendent-ambition`/7bacd9c3, Impala = `captivating-solace`/impala-fleet-manager) + `.env.local`.

## Statement design (port of AGRA report)
Same visual system as `agra-foodsystems-dashboard/src/lib/exporters.ts`: Fraunces serif title, Geist Mono uppercase meta/section labels with wide tracking, Archivo body, white page, hairline rules, light-grey table header, mono footer "Nilo · p.N".
- Header: Nilo mark + "NILO GARAGE · PARTS & SERVICES", "STATEMENT" tag.
- Title "Parts Statement — Royal Express", meta "PERIOD · NOV 2026 · STATEMENT NILO-RE-2026-11 · ISSUED 03 DEC 2026".
- Summary paragraph (units consumed, vehicles served, total due).
- Key list (status dots): total due, units, vehicles, top part.
- Tables: by vehicle (plate, parts, amount); detailed lines (date, code, item, vehicle, qty, unit cost, amount, invoice ref); totals row.
- Footer: invoices referenced · issued by · page.
- Rendering: a print-styled HTML page + `window.print()` with `@page A4` and `break-inside: avoid` on rows — real selectable text, clean page breaks (AGRA's html2canvas approach slices rows across pages and produces image-only PDFs; not acceptable for a billing document). Fonts self-hosted.

## Ingesting the two existing inventories (added 2026-11-08)
Source: `inventory_items` in RE (hymrav…, 1,058 rows, 587 distinct names) and Impala
(depesjav…, 935 rows, 714 names). Rows are purchases with a receipt; stock today is
computed as purchased − "Name (Qty: N)" strings in `maintenance_records.parts`.

Import is a script (dry-run first, writes a review report, then a commit run). Every
Nilo row keeps `source_company` + `source_id` (the original uuid). Unique
(source_company, source_id) makes the import re-runnable without doubling anything.

**Dedup rules**
1. **Split shared orders → one lot.** Rows that are one order halved between the two
   apps (description has "dividida com" / "contentor dividido", same item, date, unit
   cost in both DBs) become ONE Nilo invoice line with the summed quantity. Found
   2026-11-08 (6 pairs, no receipt, entered today):
   | Item | RE | Impala | Nilo lot |
   |---|---|---|---|
   | Pneu Roadking A1066 315/80R22.5 | 137 | 137 | 274 |
   | Calço WVA29087 | 150 | 150 | 300 |
   | Cinta Higer B220*208*16/10.8 | 320 | 320 | 640 |
   | Cinta King Long frente 130*184*14.5 | 160 | 160 | 320 |
   | Cinta King Long trás 180*184*14.5 | 160 | 160 | 320 |
   | Silentbloco 50*16 | 50 | 50 | 100 |
   Unit cost is the same in both halves (cost + freight + 30% margin), so the lot keeps it.
2. **Likely duplicates → your yes/no, never auto-merged.** Same receipt file (Storage
   eTag+size, so no 4.5 GB download) + same item + qty + unit price. Dry run 2026-11-09
   found real invoices that repeat identical lines (3 × "Material do PINTOR" 12,000 Kz on
   one paint receipt), so auto-merging would drop real purchases. 14 groups.
3. **Look-alikes** (same day + item + qty, different receipts) → your yes/no. 50 groups.
4. **One catalog name per part.** "CALÇO", "JOGO DE CALCO", "Brake disc pads",
   "Jogo de Calços"… are one part. Import proposes groups (accent/case/plural-folded
   name + size codes like 315/80R22.5, 12R22.5); user confirms in a review screen;
   the confirmed map is saved and reused. Variants that differ by spec (315/80 vs
   12R, Golden Crown vs Roadking, front vs rear) stay separate.
5. **Junk rows** (qty/price ≤ 1, e.g. "Compra de Pneus e Abastecimento" 1 × 1 Kz)
   are skipped and listed.

**What becomes stock.** History (all purchases + consumption) is imported read-only
for traceability and reports. QR units are only created for stock that physically
exists: the computed balance per catalog part (both companies pooled) is the
*suggested* count on the stock-take sheet; the shelf count is what gets labelled
(phase 8). The new China/Roadking lots arrive as normal labelled lots.
